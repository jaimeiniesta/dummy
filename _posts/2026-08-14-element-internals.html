Seven behaviours that changed between axe-core 4.12.1 and 4.13.0. Each one is a pair: the element that changed, and a control element that behaves the same in both versions. Scan this page with both engines and diff the results — the control tells you the difference is real and not an artefact of the page. Case 1, Element Internals, is the headline change and is broken into six sub-cases; the rest are single pairs.

1. Axe now reads the role set through Element Internals

A custom element can declare its own ARIA role in JavaScript, without any attribute in the HTML: 

this._internals = this.attachInternals();
this._internals.role = 'progressbar';

4.12 could not see that role. Faced with a custom element carrying ARIA attributes, it had nothing to validate them against, so it filed the whole thing under needs review. 4.13 reads the role and decides. This section has six sub-cases, because this is the change worth exercising properly.

1.1 The same attribute, opposite verdicts

aria-checked is correct on a checkbox and meaningless on a progress bar. Nothing in the HTML says which is which — only the internals do.

Correct: internals role checkbox

Wrong: internals role progressbar, identical attribute

4.12.1: both are aria-allowed-attr needs review. Same verdict for both, because 4.12 cannot tell them apart.
4.13.0: the checkbox is clean, the progress bar is an aria-allowed-attr violation.

1.2 Five more combinations 4.12 could not judge

Each of these puts an attribute on a role that does not allow it.

  • progressbar + aria-multiline
  • checkbox + aria-valuenow
  • heading + aria-selected Section title
  • textbox + aria-checked
  • tab + aria-level Overview

4.12.1: all five are aria-allowed-attr needs review.
4.13.0: all five are aria-allowed-attr violations.

1.3 The other direction: five false alarms that go away

Here the attribute is allowed on the internals role. 4.12 still asked a human to check, because it did not know the role. 4.13 confirms and says nothing.

  • progressbar + aria-valuetext
  • heading + aria-level Section title
  • textbox + aria-multiline
  • slider + aria-orientation
  • combobox + aria-expanded

4.12.1: all five are aria-allowed-attr needs review.
4.13.0: all five are clean.

On a site built out of web components this direction is the one you will notice. Every custom element carrying a legitimate ARIA attribute stops generating a manual-review item.

1.4 Not only about ARIA attributes

A button swallows its children in the accessibility tree, so putting a link inside one hides the link. The rule that catches this needs to know the element is a button.

Changed: internals role button wrapping a link

Inner link

Control: same structure with the role in an attribute

Inner link

4.12.1: only the control is a nested-interactive violation.
4.13.0: both are.

4.12 also files an aria-prohibited-attr review item against the custom element, for the aria-label it needs in order to have a name. That is case 2 below.

1.5 The limit: internals in a private field

Axe finds the internals object by probing the property names _internals, internals and internals_, plus symbols named internals and privateInternals. A real # private field is unreachable from outside the class, so none of that works.

Changed: internals on this._internals, as in 1.1

Control: same component, internals in #internals

4.12.1: both are aria-allowed-attr needs review.
4.13.0: the first is a violation. The control stays as needs review, exactly where 4.12 left it.

Write your components with a readable internals property and the extra checking comes for free. Hide it in a private field and axe treats the component as a black box.

1.6 What this does not enable

Most axe rules pick their candidates with a CSS selector such as [role="progressbar"] or [role]. A role that exists only in the internals never matches those selectors, so the element is never handed to the rule at all.

Internals role, no accessible name:

Control: the same role and the same omission, written as an attribute

4.12.1 and 4.13.0 alike: the control is an aria-progressbar-name violation. The custom element is reported by neither version.

So the reach of this feature is narrow: it changes the outcome of aria-allowed-attr, aria-prohibited-attr, aria-conditional-attr and nested-interactive, the rules whose selector is universal. Missing names, missing required attributes, missing required children and duplicate landmarks all stay invisible when the role lives in the internals.

2. aria-label on a custom element is no longer prohibited

4.12 treated any unknown element as one that cannot carry its own accessible name. That produced a false positive on every custom element with an aria-label. 4.13 exempts custom elements from the rule.

Changed: custom element with only an aria-label

Control: the private-internals version, same markup

4.12.1: both are aria-prohibited-attr violations.
4.13.0: both are clean.

The control is clean too, which is the point: the exemption is granted by the element name being a valid custom element name, not by axe managing to read the internals. This fix and the one in case 1 are independent.

3. role="image" is now recognised as a synonym of role="img"

Changed: role="image" with no accessible name

Control: role="img" with no accessible name

4.12.1: the first is an aria-roles violation (unknown role). The control is a role-img-alt violation.
4.13.0: both are role-img-alt violations.

Nothing was fixed here and nothing was broken — the same element is reported under a different rule. Browsers map image to img, so the useful message is the missing accessible name, not the spelling of the role.

4. Deprecated drag-and-drop attributes are flagged for review

Changed: aria-grabbed

Draggable card

Changed: aria-dropeffect

Drop zone here

4.12.1: both are clean.
4.13.0: both are aria-allowed-attr needs-review items.

Both attributes were deprecated in ARIA 1.1 and no browser or screen reader implements them. They land in needs review rather than violations because removing them cannot break anything, but axe will not assert that on your behalf.

5. A whitespace-only alt now counts as empty

Changed: alt=" " — a single space

Control: alt="" — properly empty

4.12.1: the first is an image-alt violation. The control is clean.
4.13.0: the image-alt violation is gone. The control is still clean.

The first image also reports aria-allowed-role in both versions, because role="presentation" is only allowed on an image whose alt attribute is literally empty. That second violation is not part of this change — ignore it when diffing, or fix the markup by removing the space.

6. A label element can no longer carry its own accessible name

A <label> names the field it points at. Giving the label itself an aria-label either does nothing or silently replaces the visible text, so 4.13 reports it.

Changed: label with visible text and an aria-label

Changed: same, but with no visible text

4.12.1: both are clean.
4.13.0: the first is an aria-prohibited-attr needs-review item, the second is an aria-prohibited-attr violation.

The split is deliberate. When the label has visible text, something readable reaches the user either way, so axe asks a human to look. When the label is empty, the aria-label is the only content and it is being applied to an element that cannot expose it, so axe calls it an error.

7. A section with a non-landmark role is no longer a landmark

Changed: two identical sections with role="group"

Filter controls
More filter controls

Control: two identical sections with no role, which stay regions

Sort controls
More sort controls

4.12.1: both pairs are landmark-unique violations.
4.13.0: the first pair is clean. The control is still a landmark-unique violation.

A <section> with an accessible name is a region landmark, and two landmarks with the same role and the same name are ambiguous. An explicit role="group" overrides the implicit region, so the pair was never a landmark conflict to begin with. 4.12 counted it anyway.
