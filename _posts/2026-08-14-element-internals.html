Seven behaviours that changed between axe-core 4.12.1 and 4.13.0. Each one is a pair: the element that changed, and a control element that behaves the same in both versions. Scan this page with both engines and diff the results — the control tells you the difference is real and not an artefact of the page.

1. Axe now reads the role set through Element Internals

A custom element can declare its own ARIA role in JavaScript, without any attribute in the HTML: 

this._internals = this.attachInternals();
this._internals.role = 'progressbar';

4.12 could not see that role, so it had nothing to validate attributes against. 4.13 reads it, and can now tell that aria-checked is meaningless on a progress bar.

Changed: internals stored on this._internals

Control: same component, internals stored in a #internals private class field

4.12.1: both report aria-allowed-attr as needs review.
4.13.0: the first one becomes an aria-allowed-attr violation. The control stays as needs review.

Both elements also carry an aria-prohibited-attr violation in 4.12 that disappears in 4.13. That is case 2 below, not this one.

Axe looks for the internals object under the property names _internals, internals and internals_, and under symbols named internals and privateInternals. A real # private field is unreachable from outside the class, so the control is invisible to axe by design. Write components with a readable internals property and you get the extra checking for free.

2. aria-label on a custom element is no longer prohibited

4.12 treated any unknown element as one that cannot carry its own accessible name. That produced a false positive on every custom element with an aria-label. 4.13 exempts custom elements from the rule.

Changed: custom element with only an aria-label

Control: the private-internals version, same markup

4.12.1: both are aria-prohibited-attr violations.
4.13.0: both are clean.

The control is clean too, which is the point: the exemption is granted by the element name being a valid custom element name, not by axe managing to read the internals. This fix and the one in case 1 are independent.

3. role="image" is now recognised as a synonym of role="img"

Changed: role="image" with no accessible name

Control: role="img" with no accessible name

4.12.1: the first is an aria-roles violation (unknown role). The control is a role-img-alt violation.
4.13.0: both are role-img-alt violations.

Nothing was fixed here and nothing was broken — the same element is reported under a different rule. Browsers map image to img, so the useful message is the missing accessible name, not the spelling of the role.

4. Deprecated drag-and-drop attributes are flagged for review

Changed: aria-grabbed

Draggable card

Changed: aria-dropeffect

Drop zone here

4.12.1: both are clean.
4.13.0: both are aria-allowed-attr needs-review items.

Both attributes were deprecated in ARIA 1.1 and no browser or screen reader implements them. They land in needs review rather than violations because removing them cannot break anything, but axe will not assert that on your behalf.

5. A whitespace-only alt now counts as empty

Changed: alt=" " — a single space

Control: alt="" — properly empty

4.12.1: the first is an image-alt violation. The control is clean.
4.13.0: the image-alt violation is gone. The control is still clean.

The first image also reports aria-allowed-role in both versions, because role="presentation" is only allowed on an image whose alt attribute is literally empty. That second violation is not part of this change — ignore it when diffing, or fix the markup by removing the space.

6. A label element can no longer carry its own accessible name

A <label> names the field it points at. Giving the label itself an aria-label either does nothing or silently replaces the visible text, so 4.13 reports it.

Changed: label with visible text and an aria-label

Changed: same, but with no visible text

4.12.1: both are clean.
4.13.0: the first is an aria-prohibited-attr needs-review item, the second is an aria-prohibited-attr violation.

The split is deliberate. When the label has visible text, something readable reaches the user either way, so axe asks a human to look. When the label is empty, the aria-label is the only content and it is being applied to an element that cannot expose it, so axe calls it an error.

7. A section with a non-landmark role is no longer a landmark

Changed: two identical sections with role="group"

Filter controls
More filter controls

Control: two identical sections with no role, which stay regions

Sort controls
More sort controls

4.12.1: both pairs are landmark-unique violations.
4.13.0: the first pair is clean. The control is still a landmark-unique violation.

A <section> with an accessible name is a region landmark, and two landmarks with the same role and the same name are ambiguous. An explicit role="group" overrides the implicit region, so the pair was never a landmark conflict to begin with. 4.12 counted it anyway.
